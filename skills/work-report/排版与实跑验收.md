# 报告与导览的排版、参考和实跑验收

> 用途：把既有暖色书卷风落实到内容编排，避免只保留页面外壳而丢掉阅读质量。
> 更新：结合实际产物和用户反馈维护；共享壳仍以 scripts/shell_template.html 为唯一实现。

## 开始写作前

读完 SKILL.md 后，先确认材料、读者和交付目标。已有报告时选质量认可且内容接近的一份，浏览器里看首页、复杂正文和末尾，记录它如何让读者找到结论、证据和边界。仅解析 CSS 或统计卡片数量不等于视觉评审；旧报告的事实和版本不能带入新稿。

形成一张简短内容安排表（保存在证据/制作目录，不必放交付正文）：章节要回答的问题 → 原始证据/数字口径 → 最合适的表达方式。先写 Markdown 事实母本，再制作 HTML 内容片段；不要直接将 Markdown 的段落/表格一一转换后结束。

## 按阅读任务选组件

| 读者需要 | 使用方式 | 避免 |
| --- | --- | --- |
| 首屏判断做成什么、还有什么边界 | 标题、版本/日期副标题、事实芯片、结论卡；有关键量化结果时用 KPI，单位/口径紧邻数值 | 首页被一整张长验收表占满；突出数字却隐去“仅到 PID 恢复”等口径 |
| 理解为什么修复有效 | 一段因果说明 + 必要的数据表 + 因果/状态/数据流 SVG | 用装饰性流程图占位；把所有步骤画成没有分支含义的方框 |
| 区分阶段和证据版本 | `.phase` 时间线，每步说明改变了什么、依据在哪里 | 将失败版和最终版的数据混算；把时间线写成会话流水账 |
| 比较前后真实效果 | 同尺度并排截图/表格，图注写条件与出处；动态效果用短视频 | 只留图片路径，或用降采样图证明像素级改善 |
| 找到风险、待验项、经验 | `.card.warnc` / `.card.note` / `.card.lesson`；详细日志放折叠区或归档 | 所有段落都包成卡片；把真实限制藏在折叠区 |
| 新人理解系统（导览） | Hero、事实芯片、按读者目标组织的阅读路径、系统图、模块内展开、文件地图 | 沿源码目录逐项罗列；把导览写成完成事项列表 |

组件是信息的表达方式，不按数量凑齐。每章保持“读者问题 → 结论 → 依据 → 含义/边界”的完整性；长报告中后段不能退化成标题和项目符号。无可证数字不造 KPI，无实际阶段不造时间线。

## 可直接使用的结构

类名与嵌套必须匹配壳。变体和 `.card` 同时使用；KPI 子项的数值/说明分别是 `.n` / `.l`；时间线编号是 `.ph`。仅写 `class="verdict"` 或自造 `.kpi-value` 不会得到既有版式。

```html
<!--TITLE: 描述性标题 -->
<!--TOCTITLE: 阅读导航 -->
<!--TOC-->
pt:结论与证据
summary|概要
mechanism|机制与依据
limits|边界与交付
<!--/TOC-->
<h1>描述性标题</h1>
<p class="sub">日期、适用版本与报告范围</p>
<div class="chips"><span class="chip"><b>范围</b> 实际验证对象</span></div>
<h2 id="summary"><span class="num">一</span>概要</h2>
<div class="card verdict"><b>结论。</b> 说明结果、验证条件和剩余边界。</div>
<!-- 有实测数字才加入；数值、单位、口径均取本次证据。 -->
<div class="kpi"><div><div class="n">实测值与单位</div><div class="l">统计口径、样本量与证据入口</div></div></div>
<ol class="phase"><li class="done"><span class="ph">1</span><b>实际阶段</b> 该阶段得到了什么证据。</li></ol>
<h2 id="mechanism"><span class="num">二</span>机制与依据</h2>
<p>说明现象、原因及验证，不复制此占位文字。</p>
<figure class="diagram"><div class="scroll">
  <!-- 在此制作本次内容所需的完整 SVG；不可省略 scroll 包裹。 -->
</div><figcaption>图号、图的含义与证据来源。</figcaption></figure>
<h2 id="limits"><span class="num">三</span>边界与交付</h2>
<div class="card warnc"><b>验证边界。</b> 尚未验证的条件与可复验入口。</div>
<div class="footer">分支、commit、版本、归档路径；随代码演进可能滞后。</div>
```

这是结构示意，不是成品内容，不把占位句交付给用户。表格、SVG、图注、章节安排由真实材料决定。导览可加局部 Hero / 阅读路径 / `.ref` 样式；不改全局壳。截图墙使用 `.image-grid`，桌面两列、手机一列；仍须检查窄屏是否可辨认。

多列证据表在手机上不能压成逐字竖排。按内容给表格合理最小宽度，并包在局部 `.scroll` 容器内（例如 `<div class="scroll"><table style="min-width:680px">…</table></div>`），让读者横向查看表格而不是拖动整页。最小宽度须根据实际列数/内容选取；两列短表不必强加。机器检查“无全页溢出”仍可能漏掉这种可读性问题，须实际看截图。

## 组装与结构检查

在任意工作目录执行时，脚本路径从本技能真实位置取得：

```text
python3 <真实技能目录>/scripts/assemble.py <证据目录>/content.frag.html <交付目录>/<标题>.html
python3 <真实技能目录>/scripts/selfcheck.py --profile report <交付目录>/<标题>.html
```

导览换 `--profile tour`。这两个命令中的路径需要替换成现场值，不能按示例创建带尖括号的目录。不要让 shell 将正文中的反引号或 `$()` 当命令执行；通过文件/补丁写入片段。

`--profile` 检查共享壳 CSS/JS 是否保持、是否依赖外部资源、锚点/标题/主体是否完整，并检查对应封面表达；它不能判断结论是否正确、叙事是否清楚或配图是否有意义。自检失败先修产物，不能改验收脚本来迁就当前报告。

## 真实浏览器与对照

有本地 Chrome/Chromium 的 POSIX 环境可直接复用标准库脚本，无需 Playwright 安装：

```text
python3 <真实技能目录>/scripts/browser_check.py --html <成品.html> --out <证据目录>/browser
```

默认测 1600×1000、1024×900、390×844；可重复 `--viewport` 定制，`--browser` 指定已有可执行程序。Chrome 沙箱受宿主限制时才显式使用 `--no-sandbox`，不要修改客户端审批配置。它使用独立临时浏览器 profile，阻断 HTTP(S)，不占用用户浏览器登录态；截图和机器断言写 `results.json`，失败返回非零。其他系统或客户端有浏览器工具时执行同等检查。脚本采样首末灯箱和一个目录目标；关键图示、长文各章的视觉审读仍由执行者补足。

1. 用当前可用浏览器实际打开最终 HTML，等待字体、图片完成；宽屏（如 1600×1000）和窄屏（如 1024×900，面向手机时再测手机宽度）各保存首页及代表性正文截图。打开本地文件也必须完整，无网络/外部资源依赖。
2. 点击目录，核目标位置、scroll-spy 高亮；滚动核进度和回顶。逐类实际点击 SVG/截图灯箱，试缩放、还原、Esc 与点空白关闭；有视频就播放并确认时间推进和画面尺寸。记录 JS 错误、横向溢出、破图及不可读的图/表。
3. 将本次截图与参考样本在**相同视口、相同缩放**下对照：主题/字号/内容宽度/侧栏保持，首屏结论和口径可见，正文有合理节奏，图表真正解释问题，后半篇证据与前半篇同样完整。保留需要修正的观察，不用组件总数或主观分数冒充“达到 Claude 质量”的证明。
4. 回查 Markdown 与 HTML 的重要数字、单位、条件、未验边界和交付状态。HTML 可增加基于母本的图示，不得出现母本没有依据的新结论；改文案后同步两版。

执行日志、截图和片段放项目证据/制作目录，不放报告附件目录。用已有浏览器工具或已有本地 Chrome 完成上述动作；不要为测试安装系统依赖。工具不能运行时列出具体缺口及已完成层级，不能只做源码检查就宣称交互通过。

## 效率与回归

复用权威壳和组件结构，保留一个内容母本、一个片段和对应证据。先解决事实与版式安排，再组装，避免写完整手工页面后返工。只重跑受影响的结构、视觉或交互检查；记录实际返工与执行时间，未做同条件测量时不声称比其他模型更快。升级技能时至少用同一份材料重做一个真实产物，并拿历史样本与旧版自检漏过的失败样本回归。
