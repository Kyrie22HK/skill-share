# Skill 入库与标准化规范

> 服务对象：skill-share 仓库（团队 Agent Skills 唯一权威库）。
> 铁律：**标准化 = 形式对齐，不是内容重写**。用户只要求形式标准化时，任何行为/质量改动须先提请裁决；已明确授权的客户端适配或改进，按该授权实施并验证，不重复索取相同授权。

## 一、三种入口，先判断走哪条

三种入口都先完整读取本文件与仓库根 [CONTRIBUTING.md](../../CONTRIBUTING.md)，再按对应模式实施并完成第五节验证。新制作时可使用当前环境已有的 skill-creator 辅助设计与检查，但其结果不能替代本库的登记、验证和交付记录；未提供该工具时直接按本规范制作。

- **新制作入库**：skill 尚不存在 → 直接在仓库 clone 的 `skills/<name>/` 下按第三节标准写正文（内容质量要求：正文只写操作步骤和判断依据，冗长细节拆到同级附属文件并写明何时读），完成后走第五节验证。
- **存量标准化入库**：skill 已存在（用户级 / 项目级 / 他处拷来）→ **先整体通读原 skill 建立理解**（不读完不动手），再按第四节做"最小改动集"，逐条列给用户确认后落盘。

- **已授权的适配/改进**：先通读现有规格、脚本和相关历史样本，保存原件与 Git 基线，列出“原能力/质量要求 → 改动 → 实跑证据”。保留原有内容深度、约束和效率机制，只修复已发现的客户端差异或质量缺口；不将本模式的授权推广到普通入库。复杂技能用隔离材料做独立前向测试，检查实际产物而不只检查格式。

## 二、定位仓库 clone

标准化动作发生在仓库工作树里（仓库是唯一权威源，不在副本上改）：

1. 优先从当前加载的 SKILL.md 真实路径定位 clone；已装软链也可核对 Claude 的 `~/.claude/skills/` 或 Codex 的 `~/.agents/skills/`。先解析软链，再定位附属文件；不同客户端不共享同名遮蔽假设。
2. 否则问用户 clone 路径；尚无 clone 先 `git clone git@192.168.8.250:skill-share/skill-share.git`。
3. 核对仓库根、当前分支、HEAD 与工作树，记录已有修改，保全即将修改的原件；不覆盖本次开始前的用户改动。
4. 改动落在哪个分支遵团队当期约定；`git commit / push` 一律等用户口令。

## 三、架构标准速查（细则与自查清单以仓库根 `CONTRIBUTING.md` 为准，两处不一致时以它为准）

- 目录 `skills/<name>/` 扁平放置，不建分类子目录；目录名 = frontmatter `name`，小写字母+连字符。
- `SKILL.md` frontmatter 只含 `name` / `description` 两字段。
- description 四要素：做什么 / 何时用 / 用户会说出口的触发关键词 / 覆盖范围。
- 附属文件平铺同级、相对路径引用；成套脚本流水线可保留 `scripts/` 子目录。
- 文档非专业术语用中文；无个人机器绝对路径、无个人项目专有内容。

## 四、质量保护红线（存量标准化的核心）

普通存量形式标准化允许的改动**只有四类**，此外正文一字不动；明确授权的适配/改进走第一节第三种入口：

1. **frontmatter 裁剪**：删多余字段前先看其信息有无价值——owner 移入 README 清单表"负责人"列，version/变更史等有用信息移入正文注记，**不是无脑删**。
2. **路径修正**：个人机器绝对路径改为相对路径或通用表述；跨 skill 引用一律写 `../<skill名>/...`（此相对路径在仓库 `skills/` 下与软链安装到 `~/.claude/skills/` 后都成立）。
3. **命名对齐**：目录名/name 不合规时改名，并全文检索旧名、逐处修正引用。
4. **布局搬移**：附属文件挪位置时，同步更新正文里的每一处引用。

**冲突裁决**：标准与质量冲突时**质量优先**——例如 skill 依赖额外 frontmatter 字段才能正常工作、description 的个性化触发词是使用者的真实说法、拍扁 `scripts/` 会破坏引用链——此时保留现状，把冲突点连同利弊报给用户裁决，绝不为了合规阉割功能。

**改动纪律**：动手前把全部拟改动列成清单（每处：位置 / 原文 / 改后 / 理由）给用户过目；已有明确范围授权时展示清单后实施，缺少对应授权才等待确认；落盘后用 `diff -r` 对比原件与入库件，核实**仅含**已确认的改动、无一处计划外变更。

## 五、入库验证与交付（必做，按适用范围留证）

1. 按第三节及 CONTRIBUTING 核对格式、命名、触发范围、文件布局与相对引用；非新制作的 skill 还须用 `diff -r` 将原件与改后版本逐条对照改动清单。
2. 安装生效与行为分开验证：Claude 使用其技能目录/调用方式；Codex 使用当前支持的目录（用户级通常 `~/.agents/skills/<name>`）及 `$<name>`。先核同名项，不覆盖已有安装；按路径可读、技能列表已发现、新会话实际使用分别记录。脚本实际跑通；报告/导览还须真实浏览器和参考样本对照，数据转换须回读输出、核覆盖与原数据保全；只跑格式检查不算行为验收。
3. 在 `README.md` 的 Skill 清单新增或更新本技能的唯一条目（名称 / 用途一句话 / 负责人）。名称必须使用 `[<name>](skills/<name>/SKILL.md)` 相对链接，与实际目录及 frontmatter `name` 一致；从 README 所在目录解析并检查目标文件存在，不写个人绝对路径或绑定分支的 GitLab 地址。更新已有技能不重复追加行。
4. 在仓库外的既有 `_ai_workspace` 任务记录或入库记录中留下可追溯事实：日期、所选入口、实际读取的规范路径、技能来源与本次授权范围、Git 基线与原有修改、改动清单、各项验证结果及证据位置、最终 Git 状态。简单修改可直接写入既有任务台账，无需另造正式报告。验证逐项区分“已验证 / 未验证 / 不适用”；记录工具是否实际使用，不把“文件看起来符合规范”写成“完整执行过本流程”。历史证据不足时明确缺口，本次补验记本次日期，不回填为过去已完成。
5. 向用户汇报改动、验证结果与限制、记录位置，以及未提交 / 已提交 / 已推送的实际状态；按已有明确授权处理提交推送。

对已有技能的小范围文档修订，按受影响项检查并说明范围，不重跑无关历史验收。新技能或行为改动仍按实际用途验证；适用验证有缺口时可以交付现有产物与下一步，但不得宣称完整入库验收通过。
