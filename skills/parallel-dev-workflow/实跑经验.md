# 实跑经验（首轮：2026-09-30 ~ 10-08）

> 来源：一个嵌入式 WiFi 摄像头项目，四条功能线（统一对话框、iOS 添加设备、相册查看页三条纯 APP 线，口令判据一条板端 + APP 线），硬件一台主板（后期另一块板交出）、一台安卓机、一台 iPhone、一台 Mac 打包机。
> 何时读：搭建完、开第一批线前读一遍；每轮收口复盘时对照增补。表中「对策」均已落进 skill 的脚本或规则。

## 摩擦 → 对策

| # | 摩擦 | 对策 |
|---|---|---|
| ① | 线拿了板 / 手机锁后回去写代码，不用也不放，别的线只能等；锁状态分不清「马上还要用」和「占着」。根因：「放锁前必须回基线」让放锁成本高，线倾向攥着 | 不是一不用就让，而是**离开硬件时预估空档**：长则回基线放锁，短则 `hold --next` 登记；阈值按归还成本定；工具用锁时自动续租 |
| ② | 共享工具在「主目录有产物、worktree 没有」的差异下露出隐藏假设：某场景驱动命令在新 worktree 里静默退出（`ls` 缺一个参数返回 2，`set -euo pipefail` 下赋值失败、函数提前退） | **开线后第一件事把所有工具的只读子命令在 worktree 里跑一遍**；工具里列文件只列真实存在的 |
| ③ | 线在声明范围外多改了几行（如应用入口文件） | 集成线合并时对照状态卡「只改」清单与 `git diff --stat`，范围外改动要线说明理由 |
| ④ | `take --wait` 各自轮询、谁先抢到归谁：排了 1 小时的线在放锁那一刻被后来者截走 | 先来先得队列；排队进程死了队位自动清；不带 `--wait` 的不插队 |
| ⑤ | 尾段只剩「同步主线 + 复验」的线：线内复验与合并后复验占两次手机和板子 | 集成线直接 rebase、合并、一次复验后收线，不再为它开会话 |
| ⑥ | 锁「过期」被当成「空闲」；旧版 `take` 会直接覆盖过期锁 | 过期须 `--force`；先用跨会话消息问持有线 |
| ⑦ | 锁只拦得住工具，拦不住设备自己回连：测试手机里留着早先演示时的设备绑定，APP 一拉起就自动加入了已交给别人的板子的热点、登录并对时 | 交出硬件时连手机侧绑定一起清；拉起 APP 前看一眼绑定列表 |
| ⑧ | 多线同时往共享笔记追加，编号撞车 | 集成线合并时按写入先后重编号，并改对方状态卡 / 证据卷里的引用 |
| ⑨ | 复验中发现的问题来自别的线留下的硬件状态（如被信道跟随改过的无线配置），不是被验的代码 | 复验失败先查硬件当时的持久状态与日志，再怪代码；交接时状态卡写明改过的持久状态 |

## 效率观察

- 三条纯 APP 线的编码与模拟器验证完全并行，真机阶段按锁串行；单条线的实际工作时长约 3–6 小时，其中两条跨了一个下班断点（隔了 8 天），靠状态卡无损接续。
- 合并冲突集中在两三个热点文件（连接逻辑、添加设备页、八语种文案），按「后合的线按语义融合」处理，没有一次需要推翻已合入的改动。
- 跨会话消息让线之间直接约硬件、通报新占用的文件，集成线只在冲突时调度；这比所有协调都经集成线转达快得多。
- 子代理只用于调研和同质小活；硬件始终由线的主会话操作。
