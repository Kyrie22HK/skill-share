# 实跑经验（首轮：2026-09-30 ~ 10-08）

> 来源：一个嵌入式 WiFi 摄像头项目，四条功能线（统一对话框、iOS 添加设备、相册查看页三条纯 APP 线，口令判据一条板端 + APP 线），硬件一台主板（后期另一块板交出）、一台安卓机、一台 iPhone、一台 Mac 打包机。
> 何时读：搭建完、开第一批线前读一遍；每轮收口复盘时对照增补。表中「对策」均已落进 skill 的脚本或规则。

## 摩擦 → 对策

| # | 摩擦 | 对策 |
|---|---|---|
| ① | 线拿了板 / 手机锁后回去写代码，不用也不放，别的线只能等；锁状态分不清「马上还要用」和「占着」。根因：「放锁前必须回基线」让放锁成本高，线倾向攥着 | 不是一不用就让，而是**离开硬件时预估空档**：长则回基线放锁，短则 `hold --next` 登记；阈值按归还成本定；工具用锁时自动续租 |
| ② | 共享工具在「主目录有产物、worktree 没有」的差异下露出隐藏假设：某场景驱动命令在新 worktree 里静默退出（`ls` 缺一个参数返回 2，`set -euo pipefail` 下赋值失败、函数提前退） | **开线后第一件事把所有工具的只读子命令在 worktree 里跑一遍**；工具里列文件只列真实存在的 |
| ③ | 线在声明范围外多改了几行（如应用入口文件） | 集成线合并时对照状态卡「只改」清单与 `git diff --stat`，范围外改动要线说明理由 |
| ④ | `take --wait` 各自轮询、谁先抢到归谁：排了 1 小时的线在放锁那一刻被后来者截走 | 先来先得队列；排队进程死了队位自动清；不带 `--wait` 的不插队 |
| ⑤ | 尾段只剩「同步主线 + 复验」的线：线内复验与合并后复验占两次手机和板子 | 集成线直接 rebase、合并、一次复验后收线，不再为它开会话 |
| ⑥ | 锁「过期」被当成「空闲」；旧版 `take` 会直接覆盖过期锁 | 过期须 `--force`；先用跨会话消息问持有线 |
| ⑦ | 锁只拦得住工具，拦不住设备自己回连：测试手机里留着早先演示时的设备绑定，APP 一拉起就自动加入了已交给别人的板子的热点、登录并对时 | 交出硬件时连手机侧绑定一起清；拉起 APP 前看一眼绑定列表 |
| ⑧ | 多线同时往共享笔记追加，编号撞车 | 集成线合并时按写入先后重编号，并改对方状态卡 / 证据卷里的引用 |
| ⑨ | 复验中发现的问题来自别的线留下的硬件状态（如被信道跟随改过的无线配置），不是被验的代码 | 复验失败先查硬件当时的持久状态与日志，再怪代码；交接时状态卡写明改过的持久状态 |


## 第二轮实跑补充（2026-10-09：两条线，一条板端 + APP、一条纯 APP；一台主板、两台手机、一台 Mac）

| # | 摩擦 | 对策 |
|---|---|---|
| ⑩ | 板子只是被连上去用、没被改动，也要排队拿锁，两条线白等 | 设备可登记为「只读共用、改动独占」：只读使用免锁、多线同时用；投板、刷包、重启、改配置、全量冒烟才独占，并先告知其他线。本轮两线全程板子零排队 |
| ⑪ | 线会话在根目录（不在 `wt/<线名>/` 里）跑 `lock.sh release --all`，被按目录认成 main，放掉了集成线正持有的板子锁 | 锁命令一律在线目录里跑（已写进第四节）；误放后线主动报告，集成线重拿并核实期间没人插进来 |
| ⑫ | IDE（VSCode）开线时自动把线工作树当仓库打开；收线删目录后不会自己关，源代码管理里挂着整编时的陈旧状态（10k 改动） | 收线或关闭一轮后提醒用户重载 IDE 窗口；磁盘与 `git worktree list` 干净即可判定是陈旧状态 |
| ⑬ | 借来的非登记设备（同事自用手机）参与测试，交还后可能在本组设备附近自动连上来 | 非登记设备只读使用免锁；交还时留正式包（记版本与是否含未合入改动）、清掉对本组设备的绑定、调试通道由用户收回 |
| ⑭ | 集成线把「两台手机同时连同一台设备」当成互相干扰而错开测试，用户纠正：这正是真实使用场景 | 设备共用的「干扰」先核是不是真实使用场景，是就列为必测项；本轮因此补测出板端保护逻辑第一次真正生效 |
| ⑮ | 线把没核过源码的推测当隐患报上来，集成线据此问了用户；线动手前核源码自己推翻了 | 附注类隐患先核再报；集成线转给用户前也先核一遍 |
| ⑯ | `close` 把本轮归档放在根目录下的隐藏目录 `.pdw-archive/`：项目另有协作工作区，前几轮的线状态卡都收在工作区里，这一轮却落在工作区外，用户看到后问「这是什么、怎么在这」 | `init --archive <目录>` 把归档指到项目工作区（记进 `conf.sh` 的 `PDW_ARCHIVE_DIR`，`close` 时用）；不给即沿用 `<根>/.pdw-archive/`。已落在根目录的归档手工挪过去并改引用 |

## 第三轮实跑补充（2026-10-10：三条线，一条板端 + APP、两条纯 APP；一台主板、两台手机、一台 Mac）

| # | 摩擦 | 对策 |
|---|---|---|
| ⑰ | 线 worktree 缺主目录的未入库产物：打包工具以之为底的基座安装包、产品构建内置的固件、插件编译要的预编译库。打包命令在 worktree 里直接失败，只读子命令跑一遍时暴露 | 开线后由集成线从主目录复制进各线，状态卡写明来源版本（已写进第三节第 3 步）；可考虑给 `line new` 加「复制清单」参数 |
| ⑱ | 会话列表只显示会话名，看不出哪个会话是哪条线；集成线一度只能给两条线发同一封分段消息 | 开工令里让各线回报线名，再把名单互相告知（已写进第三节第 5 步） |
| ⑲ | 两条线交叉持锁：一条拿着手机等打包机，另一条拿着打包机等手机，各等了十几、二十几分钟 | 集成线看 `pdw.sh status` 的排队与「最近 N 分钟前」，发现互等即调度：闲的一方直接线间交接（免回基线），打包机打完包即放 |
| ⑳ | 用户不想被多条线分别打断，要求线的问题先报集成线、由集成线决策 | 开工令写明；线报问题须附暂定方案与理由，集成线大多当场拍板，只把不可逆、花钱、品牌观感、合并推送这类转用户 |
| ㉑ | 集成线开线时漏说关键前提（资料的来源 / 归属），还凭印象把调试页路径当成产品页写进状态卡，线一度按错的前提走 | 状态卡「已知事实」先问清来源、路径读码核实；被订正后同步改任务卡与各卡，并转告受影响的线 |
| ㉒ | 集成线给线的结论基于改动前的代码，线早已改了那一块，指令作废 | 对他线正在改的区域下结论前，先看该线最新进展（会话记录 / 状态卡） |
| ㉓ | 集成线手写的事件时刻凭估计，偏差最多一小时 | 手写事件前先取当前时间；收口前按会话记录与 git reflog 校正 |

## 效率观察

- 三条纯 APP 线的编码与模拟器验证完全并行，真机阶段按锁串行；单条线的实际工作时长约 3–6 小时，其中两条跨了一个下班断点（隔了 8 天），靠状态卡无损接续。
- 合并冲突集中在两三个热点文件（连接逻辑、添加设备页、八语种文案），按「后合的线按语义融合」处理，没有一次需要推翻已合入的改动。
- 跨会话消息让线之间直接约硬件、通报新占用的文件，集成线只在冲突时调度；这比所有协调都经集成线转达快得多。
- 子代理只用于调研和同质小活；硬件始终由线的主会话操作。
- 第三轮：三条线 15:52 开线，约 1h45m / 2h15m / 2h55m 依次合入；等外部资料（算法后处理代码）期间，线按推断值往下搭、参数集中成配置，资料到后只改配置。两条 iOS 线用不依赖基座的原生小壳在模拟器上出方案，真机只用于定稿，手机争用明显下降。

| ㉖ | 借机（同事私人手机）接入与归还的一串坑：命令占位符被原样敲入、上次「保留数据」卸载接上旧绑定、新系统装包整页确认、10 分钟锁屏、机主的日志限流 | 给用户的命令填实际值；基线＝不带 -k 卸载 + 列已卸包为空；装包确认按文字代点；熄屏时间改了记原值归还前改回；机主的应用与设置不动；手机一测完立刻按基线归还、设备下线 |
