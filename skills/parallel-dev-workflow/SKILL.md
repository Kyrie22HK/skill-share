# 并行开发工作流（worktree 功能线 + 硬件租约锁 + 集成线）

> 沉淀自一个嵌入式摄像头项目的首轮实跑（2026-09-30 ~ 10-08，四条功能线：三条纯 APP、一条板端 + APP；一台主板、一台安卓机、一台 iPhone、一台 Mac 打包机）。
> 核心判断：**瓶颈在硬件不在脑力**——编码、编译、模拟器验证可以并行，上板 / 装机必须排队；项目知识是厚上下文型的，一条线从头到尾一个会话攒着最省。

## 一、先研判：这批工作值不值得开线

开线前先判断，不是功能一多就开：

| 情形 | 做法 |
|---|---|
| ≥ 2 个相互独立的功能同时推进，编码可并行、共享硬件稀缺 | 开线 |
| 几个功能改的是同一批文件（冲突成本 > 并行收益） | 串行，或让后开的线等前一条合并 |
| 一批同质、独立、验收明确、不碰硬件的小活（换 7 处同类调用、文案审校） | 不开线：由某条线的会话临时起子代理 / Agent teams |
| 某条线只剩「同步主线 + 复验」 | 不必再开会话：集成线直接 rebase、合并、一次复验后收线 |
| 单人单功能 | 不开线，但工具照常拿锁，养成习惯 |

## 二、形态与角色

```
<外层根>/
├── <仓库A>/  <仓库B>/       集成线（main）的主目录：只做合并、回归、刷板，不做功能开发
├── wt/<线名>/               功能线：.wt.env（目录 / 端口）+ 各仓库的 worktree（分支 feat/<线名>）
├── .locks/                  资源锁（一资源一文件，排队在 <资源>.q/）
└── _ai_workspace/<项目>/
    ├── tools/               wt.sh lock.sh wt_auto.sh wt.conf（+ 项目自己的构建 / 部署工具）
    ├── wt/<线名>.md         状态卡（线的接续点）；收线后移入 wt/_done/
    └── current_task.md 等   总账：只由集成线改
```

| 角色 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 调度 | 用户 | 开线 / 收线、定优先级、裁决体验口味 | — |
| 功能线 | 每线一个会话 | 编码、编译、模拟器 / 静态验证；就差上板时拿锁 → 验 → 回基线 → 放锁；维护状态卡与证据卷 | 不改总账、决策日志；不碰别的线声明的文件；子代理不碰硬件 |
| 集成线 | 主目录的会话 | 合并 `feat/*`、回归、刷板、推送、更新总账与决策、`wt.sh rm`、出报告 | 不在主目录做功能开发 |

## 三、搭建（每个项目一次）

1. 把 `scripts/` 下的 `wt.sh`、`lock.sh`、`wt_auto.sh` 拷到项目 AI 工作区的 `tools/`（不进业务仓库），`wt.conf.example` 拷成 `wt.conf` 填好：仓库与基线分支、资源表与闲置阈值、板子 IP 映射、端口基数、线环境变量。**阈值按归还成本定**：板子回基线约 1 分钟 → 10 分钟；手机要卸包清绑定 → 20 分钟；没有归还成本的工具锁 → 5 分钟。
2. 接入：项目里每个动硬件的工具开头 `source wt_auto.sh`，改硬件的分支前 `need_lock <资源>`（板子用 `need_lock "$(board_res_of_ip "$IP")"`）；只读子命令（查状态、对账）放行。工具里的目录 / 端口变量一律写成 `${VAR:-默认值}`，`.wt.env` 才能覆盖。
3. 写项目规范：照 [项目规范模板.md](项目规范模板.md) 落成项目文档，重点填**每种硬件的归还基线**（回到什么状态才能放锁）和**共享件清单**（同一时刻只许一条线改的文件）。
4. 在项目 CLAUDE.md 的启动协议里加「启动线」分支：照 [CLAUDE段落模板.md](CLAUDE段落模板.md)。
5. 自检：`bash scripts/selftest.sh`（临时目录里跑 34 项，约 40 秒）。再在项目里开一条试验线，**把所有项目工具的只读子命令在 worktree 里跑一遍**——主目录有产物、worktree 没有的差异会让工具露出隐藏假设——然后收掉。
6. 外层根若本身就是 git 仓库，把 `wt/`、`.locks/` 加进 `.gitignore`。

搭完、开第一批线之前，读一遍 [实跑经验.md](实跑经验.md)。

## 四、日常运转

**开线**（集成线或用户）：`wt.sh new <线名> [--repos a,b] "<一句话目标>"`，再把状态卡补全——用户原话与来由、只改 / 不改清单（与在跑的线交叠的文件写明谁先合）、研判与验收标准、要用的硬件。告诉用户：新开会话说「启动线 <线名>」。

**起手**（功能线会话）：`wt.sh start <线名>` 读简报与状态卡 → `cd <外层根>/wt/<线名>`（此后工具按目录自动用本线的目录与端口）→ 复述「做到哪 / 下一步」→ 得到确认再动手。不读总账。

**用锁**：
- 动硬件前 `lock.sh take <资源> "<用途>"`；被占就 `--wait` 排队（先来先得，队位在排队进程死后自动清）。
- **每次离开硬件时预估下次要用还要多久**：空档 ≥ 阈值就回基线放锁；没一会就要用的 `lock.sh hold <资源> --next <N>m "<回来要做什么>"`，别人据此决定等还是先干别的。
- 工具经 `need_lock` 放行时自动续租，用着的锁不会到点过期。
- **别人的锁过期不等于不用**：先发消息问持有线，确认后才 `take --force`。
- 放锁前硬件回到项目规范写的基线；**锁只拦得住工具、拦不住设备自己回连**——交出硬件时把手机侧的旧绑定一起清。

**线之间直接沟通**：会话间能互发消息时，线之间直接约硬件交接、通报新增占用的文件，集成线只在冲突时调度。

**功能线收尾**：覆盖式更新状态卡（做到哪 / 卡点 / 下一步 / 硬件记录）、证据卷写清验的什么、判据、结果、用的版本；`lock.sh release --all`；平台级经验写共享笔记（多线同时追加会撞号，集成线合并时重编号并改引用）。功能线不出报告。

**集成线合并**：
1. 审范围：状态卡「只改」清单对照 `git diff --stat`，范围外改动要线说明理由；提交信息合规。
2. 合并：能快进就快进；有冲突时**后合的线按两边的语义融合**（读双方状态卡与提交说明，不是机械取并集），合并后编译所有构建形态。
3. 回归：快进合入的就是线里验过的提交，不重复验；rebase 过或解过冲突的，按项目冒烟与关键场景复验后再推送。
4. 收线 `wt.sh rm <线名>`（未提交、未合并、还持锁的会被拒）；更新总账、进度、决策日志；共享文档里被这条线弄过时的地方一并改掉；通知其余在跑的线基线前进了。
5. 一轮线收齐后出一份汇总报告，复盘摩擦点、补进实跑经验。

## 五、子代理 / Agent teams / Workflow 放在哪

- 功能线内子代理：大范围代码调研、并行读文档、长编译时同时写别的、实验数据分析。**不碰硬件**，结论回主会话核验。
- Agent teams：只用于同质、独立、验收明确、不碰硬件的一批小任务，由那条线临时起、起完自己验一遍。
- Workflow：提交前多维度审查一类确定性流水线；不用于探索型开发。
- 主形态始终是一线一会话一 worktree。
