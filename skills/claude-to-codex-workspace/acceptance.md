# 迁移验收与证据

> 用途：检查迁移是否能支持实际接续，并区分不同层级的验证。
> 更新：根据本次结构选择适用项；验收记录写入目标工作区维护目录。

## 先保存什么

迁移前记录目标仓库路径、分支、HEAD、状态，现有入口与任务卡，以及即将替换或删减文件的可恢复原件和 SHA256。只需保全会受影响的唯一信息；已有可靠版本来源时可引用它，不重复备份整区。

维护记录可采用 `baseline.json` / `before/` / `changes.json` / `verification.json`，也可沿用项目现有形式；这些文件名不是强制要求。每个证据应有时间、范围和结果，不只列命令。改动清单列新增/修改/删除路径、迁移后哈希与旧原文位置。

## 静态检查

| 检查 | 通过条件 |
| --- | --- |
| 入口可达 | 从用户实际启动位置能自动发现或按给定路径显式读取；无循环和断链 |
| 必要规则 | 原有效工程契约、授权边界、证据验收和收尾要求都有落点；例外有理由 |
| 项目隔离 | 目标入口不把兄弟入口/任务卡列为默认必读；独立入口包含所需完整规则 |
| 原文与任务 | 快照哈希匹配；活跃任务、卡点和唯一历史信息仍可找回 |
| Git 与文件范围 | 分支和 HEAD 未被迁移意外改变，原有用户修改保留，新增改动符合范围 |
| 引用与安装 | 相对路径解析基准清楚；链接目标存在；技能没有形成多份活副本 |
| 当前与历史 | 已废弃入口、冻结记忆、旧授权、旧 IP/版本均未冒充现行事实 |
| 约束保留 | 根入口、文档位置、Claude 共存等符合用户选择；未擅改全局权限 |

对 Git 工作树的判据是“与迁移前相比只有预期变化”，不是无条件要求干净。若用户允许在代码仓库放入口，对应文档变化可以是预期差异；代码、设备或依赖改动需要另有任务依据。

对非发现链文件，不以存在 `AGENTS.md` 作为自动加载证据；对包含 Markdown 代码例子的模板，不将其中示例路径误报成断链。检查器如只识别某种链接语法，应注明覆盖范围。

## 启动与行为检查

按项目选择适用情境。可先做桌面推演发现矛盾；下面的“实际通过”需真实会话或工具轨迹，不能用推演代替。

| 输入/情境 | 预期可观察行为 |
| --- | --- |
| 只说“按启动协议启动项目 A” | 读 A 的入口和任务卡，核 A 仓库，简报；不执行历史待办 |
| “启动项目 A，并完成指定任务” | 恢复上下文后继续已有授权工作，不因旧“确认再动手”重复停下 |
| 同目录有 A/B 两项目 | 启动 A 时不批量读取 B 的入口、任务和历史；实际跨项目任务再定向查询 |
| 旧任务写有“本 session 全权授权” | 不把它延伸到本次提交、推送或设备修改 |
| 任务卡分支/IP/版本与现态冲突 | 报告并核实差异，不机械切分支或操作旧设备 |
| 某技能文件可读但未被客户端发现 | 可显式读取，状态写“按路径可用”；不声称注册成功 |
| 用户要求根目录没有入口 | 按项目路径启动有效；检查误加的 root/override/fallback 不会绕回旧方案 |
| Claude 与 Codex 共存 | 两个入口均指向正确项目，公共规则只有一个维护来源，导入无循环 |

供新会话使用的显式提示示例：

```text
按启动协议启动 <项目名>。入口是 <项目 AGENTS.md 的实际路径>。
本次只恢复上下文和简报，不执行旧待办。请列出实际读取的入口、
任务卡与仓库状态来源，并说明当前承接点、卡点和建议下一步。
```

验证自动发现时，另外从用户指定的启动目录开新会话，不预先给出入口内容，检查客户端加载来源。显式读取测试只能证明显式读取有效。

不能启动新会话时，交付这条可执行提示、启动目录和预期结果，标明“待新会话验证”。不得为制造通过记录擅自开启额外付费代理、改权限或连接生产设备。

## 证据层级与收口

| 层级 | 能证明 | 不能证明 |
| --- | --- | --- |
| 静态检查 | 文件、链接、原件和结构满足检查条件 | 客户端实际加载、模型行为正确 |
| 当前会话显式读取 | 路径可达，内容可以读入 | 新会话会自动发现 |
| 新会话实际加载 | 给定客户端、目录、配置下加载成立 | 换环境仍成立、全部业务工作流可执行 |
| 实际工作流执行 | 本次工作在已测条件下完成 | 所有历史工具、所有设备已迁移验证 |

纯工作区文档适配通常无需固件构建、设备部署或全量测试；后续业务任务仍沿用原项目验收标准。如果发现严重信息丢失或启动误执行，修正并重跑受影响检查；无需反复执行无关测试。

最后给出入口、使用方式、变更范围、实际验证层级、遗留缺口及恢复入口。更新本次涉及的工作区事实性维护记录；不要同时改未涉及项目的任务台账。

## 恢复

恢复前逐项比较当前文件与迁移后哈希清单。当前内容未变时可按已授权范围恢复原件；已有后续编辑时先合并，不批量覆盖。新增文件按清单处理，原始记忆与唯一备份不可随迁移回退一起清空。

用户后来修改的启动方式优先于早期迁移方案。旧的成功记录只说明当时通过，不能据此恢复已被用户撤销的入口。恢复文档通常不需要 reset、切业务分支或刷设备。
